阅读器逻辑不重写（编码检测 / 章节解析 / 进度存储是已验证的纯逻辑），**重开的是交付链与阅读界面**：干掉「C# 单文件 exe 解压到临时目录 + 按修改时间挑 dist」这条脆弱路径，从「双击必开」重新立地基。

## 1. 复盘：v1 为什么会走到「重来」

- 最近三个提交（`d4d83f8`、`9e6bd18`、`c31afc6`）全花在壳与打包上；2026-09-15 21:01 的启动失败仍然出在壳。
- 证据：`%TEMP%\novel-reading-demo.log` 显示 `NavigationCompleted success=False error=ConnectionAborted`；v1 的壳（`MainForm.ResolveDistDir()`，随 v1 冻结已删除，`git show v1-mvp:desktop/NovelReadingDemo/MainForm.cs`）在临时解压目录里「取最近修改的 dist」，本次把页面映射到了非当前运行的解压目录，页面加载失败 → 白屏。

## 2. v2 验收标准（全部可观察，不达标即未完成）

| # | 标准 | 验证方式 |
| --- | --- | --- |
| A1 | 双击产物 ≤2 秒出现可交互界面，连续 5 次冷启动全部成功 | 关掉再开，逐次记时间与结果 |
| A2 | 10 MB GBK 小说 ≤5 秒显示第一章 | 真实小说样本 |

## 3. 技术方案

### 3.1 交付形态（关键决策）

| 方案 | 做法 | 代价 | 适用 |
| --- | --- | --- | --- |
| **A（建议）单文件 HTML** | Vite 构建成 1 个内联全部资源、无外部请求的 `index.html`，双击用系统浏览器打开 | 没有独立窗口/图标；本地文件靠拖拽或文件选择 | 想彻底摆脱 .NET / WebView2 / 临时解压 |
| B 文件夹式 exe | .NET 发布为**非单文件**：`release/novel-reading/novel-reading.exe` + 同级 `dist/`，壳只认 `AppContext.BaseDirectory\dist` | 目标机需 .NET 10 Desktop Runtime；分发是目录或 zip | 想要独立应用窗口 |
| C 单文件 exe（v1 老路） | 单文件 + 嵌入 dist | 白屏风险已知且不可复现 | v2 不再作为默认 |

建议：**先做 A，再按需加 B**。B 的做法与 A 共用同一份 `dist` 产物，不重复开发；C 留到最后、且必须通过 A1 的 5 次冷启动验收才允许发布。

### 3.2 保留 / 重做 / 删除

| 处理 | 内容 | 原因 |
| --- | --- | --- |
| 直接搬 | `src/core/encoding.ts`、`chapterParser.ts`、`storage.ts` 及对应单测 | 纯逻辑、无 UI 依赖、已有测试兜底 |
| 重做 | 阅读界面（布局、翻页、目录、设置）、空态与报错、进度模型（章节 + 段落） | 用户不满意的集中区 |
| 重写 | 打包脚本与启动路径：只认固定目录，找不到就报明确错误，禁止「猜目录」 | 白屏根因 |
| 已删除 | v1 的 C# 壳（含「取最近修改的 dist」启发式）与针对旧壳的打包断言 | 脆弱假设 |
| 迁移 | 进度键从「文件名 + 大小」换成内容 hash，并做一次性回填 | 同名文件串进度 |

### 3.3 规模

v2 仍是 1 个 Web 应用 + 1 个可选壳，代码量与 v1 同级；不引入后端、不引入数据库（浏览器本地存储足够）。

## 4. 里程碑（每步一次提交，各自可验收）

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| M0 冻结 | v1 打 tag 存档；v2 在新分支（`codex/v2`）开工 | `git tag` 可回退 |
| M1 交付先行 | 打通方案 A 的构建：产物 1 个 HTML，双击能打开、能拖入 TXT 读完一章 | A1（可先用浏览器标准替代双击计时）+ A4 |
| M2 核心搬运 | `core` + 单测搬入并跑绿；进度键换内容 hash（含单测与旧数据回填） | A6 |
| M3 阅读界面重做 | 阅读优先布局、字号/行距/页宽、日间夜间、目录、上下章、进度保存与恢复 | A2、A3 |
| M4 打磨 | 键盘快捷键（←/→ 翻章、空格翻页、Ctrl+O 打开）、拖放、空态与报错文案 | 手工清单 |
| M5 验收发布 | 跑完 A1–A6；产出 zip + 一页使用说明；按需加方案 B 的壳 | 交付 |

顺序要点：**M1 必须排在 M2 之前**。先让「一定打得开」变成事实，后面所有验收才有意义。

## 5. 成本与风险

- 预估：低于 v1 的重建（v1 从 0 到 MVP 约 5–6 小时活跃时间）。v2 复用 core、范围更窄、不碰新格式，主要工作量在 M3 界面。
- 风险 1：又回到单文件 exe → 白屏复现。对策：C 方案最后做，且过 A1。
- 风险 2：界面重做没有判据，又变成「细节不满意」。对策：M3 只按 A2／A3／A6 验收，视觉以「能长时间读下去」为准，不做玄学。
- 风险 3：v1 已有进度无法继承。对策：M2 做一次性回填（文件名 + 大小 → hash）。
- 省钱约定（沿用 `simple-accounting` 的实测结论）：一个里程碑一个会话；默认不截图，让用户自己操作确认；必须截图时只截相关区域且一轮 ≤2 张；一条命令跑完「改 → 编译 → 测试 → 验证」；工具输出只保留结论行。
